

The goal for the demo is a 'AI engineering pipeline builder'.
After getting visibility on multiple real world use cases, this is the core of all projects.

It allows you to 
1. validate the output of an LLM in a defined structure
2. outline the modules and pipeline to get from input to output in the way to get the most performance.


What i mean by that is the you need to have intermediate steps which are used to
1. check your work
2. seperate out tasks to make things less difficult for the llm
3. make sure your development is modular and reusable for later projects.
4. cache and avoid recalculating and billing yourself for steps you've already completed.


the UI should the following window for each project inside the project selector.

1. Structure builder
  using code or a UI to build pydantic / zod model (structures) that your LLM should output to
2. Pipeline builder
  where does the model take inputs?
    For example maybe you input a legal pdf, convert it to text and atomic rules to assess.
    Then you take in a company outline after that step and see if the company is adhereing to those rules or if they might be liable for damages.
  What types of inputs are they? excel, word, pdf, json.

  you should be able to see
    the last run output and input from each step
    the history with times for each intput and output 
    in other words
    document_input_latest.txt
    document_input_11Jun2026_12pm45.txt
    these should be saved in the documents tab under 'previous runs'

  include some metrics like average latency and average cost.
  The most important part is that each steps shows their input and output model, and the UI points out where a pipeline is invalid because a input flows into an output that isn't equal. 
  schema validation isn't an explicit step in the pipeline, it's implicit in the validation of every input and output from every step.
  you should not include a seperate schema validation step.

  please have the input output schema visible without clicking on each individual step. 
    input : ...
    output : ...

  please have a run button on each step which has a cached or has an input ready. this should go dark if the pipeline is invalid.



3. AB testing
  test what approach works best in the pipeline
  You might want to compare what works best between
    3.1 A single LLM call
    3.2 A RLM call (Recursive Language Models)
    3.3 A full claude code instance tackling your problem. 
    3.4 A claude code like system running on a cheap chinese model for cost efficiency.

  Which is the best choice will be evaluated by an llm, 

4. Inference
  running your pipeline with a simple drag and drop system, no need to depoy anything like a custom pipeline. it should be easy to send a link to others of just this page.
  please have a run button on each step which has a cached or has an input ready. the cache files should be saved in documents tab probably as json files, with a pydantic / zod structure attatched which should be static and valid.
  this tab should show the same errors if the input doesn't feed into the output.

5. Logging
  there should be a page dedicated to logging of all the pipeline inference. This should have syntax highlighting where json or markdown is used in the UI, there should be a download button. 
  Additionally, there should be a 'high level' page where logging output is in easy to visualise HTLM rather than detailed technical logs, this html should include progress bars and be shown as progress in the 4.inference tab.

6. Documents
  this contains documents uploaded during inference or training with a label of which. 
  avoid duplicates using hashing as an ID.

7 Billing
  a graph of billing from different llm models, services
